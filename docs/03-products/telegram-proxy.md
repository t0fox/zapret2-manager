# Telegram Proxy

Telegram Proxy — отдельный optional-продукт со своей страницей и lifecycle.
Сначала проверьте: установлен ли provider, какой provider выбран, запущен ли
процесс, есть ли health и какая версия установлена.

Поддерживаемые в текущем репозитории варианты — `tg-ws-proxy-go` и
`tg-ws-proxy-rs`. На первом экране показываются назначение и состояние, а не
внутренний adapter ID.

## Профили подключения (Settings)

Верх Settings — «Профиль подключения»: **Рекомендуемый / Прямой /
Пользовательский**. Профиль описывает только маршрутизацию; включение,
автозапуск, доступ из LAN и порт — пользовательские connection facts и
профилем не меняются.

- **Рекомендуемый** (default для новой установки): port 1443, upstream
  default-domains по **Flowseal** canonical-списку (Rust
  `TG_DEFAULT_DOMAINS=true`; Go — его дефолтный `CFPROXY_DOMAINS_URL`),
  `cf_priority`, pool 4. Свои CF/worker/MTProto/outbound значения остаются
  пустыми, пока пользователь их не задаст.
- **Прямой**: только прямое подключение к Telegram.
- **Пользовательский**: определяется автоматически по routing-сигнатуре.

Первичная инициализация материализует recommended-конфиг с **LAN-адресом
роутера** в HOST (loopback-only bind — главная причина бесконечного
«Подключение…» на клиентах). Существующий пользовательский config при
upgrade/reinstall и переключении Rust↔Go не перезаписывается. «Восстановить
рекомендуемые» показывает diff основных полей до применения и не трогает
secret. Normal view: Прокси / Автозапуск / Доступ из локальной сети /
Адрес для подключения (advertised) / Порт; всё остальное — в свёрнутых
«Дополнительных настройках».

## Статусная модель (Обзор)

«Работает» — ТОЛЬКО локальное здоровье (процесс + слушатель) И подтверждённая
доступность Telegram DC. «Работает с ограничениями» — локально жив, upstream
не подтверждён. «Не работает» — отказ процесса/слушателя. Health chain:
Процесс → Слушатель (реальный адрес:порт) → Telegram. Никаких зелёных
статусов из process+listener alone.

## Операции

Install/update/downgrade/switch/remove идут через durable operation record
(`/tmp/zapret2-manager/proxy-provider-operation.json`): стадии
Подготовка → Проверяем релиз → Скачиваем → Устанавливаем → Запускаем →
Проверяем → Готово с determinate-прогрессом; reload страницы посреди
операции подхватывает RUNNING-запись. Провайдеры взаимоисключающие — при
switch конфликтующий пакет снимается до установки. Failure показывает этап,
человеческую причину и состояние отката; technical code — в деталях.

## Релизы и changelog (Компонент)

GitHub release discovery сохраняет для КАЖДОЙ версии полную идентичность
(`releaseId`, `tag`, `name`, `publishedAt`, `prerelease`, `draft`, `body`,
`htmlUrl`) — changelog следует за выбранным в dropdown релизом, без
глобального «latest» объекта. Пустой body upstream — валидное состояние
(«Описание изменений для этого релиза не опубликовано.»); дата, тег и
официальная ссылка показываются всегда. Ссылка «Открыть релиз на GitHub» —
только официальный upstream-репозиторий выбранного провайдера.

Доступные действия зависят от backend: **Install**, **Start**, **Stop**,
**Restart**, **Update**, настройки и удаление. System → Components не является
установщиком TG. Кнопка на Главной должна вести сюда.

Конфигурация и секреты принадлежат lifecycle provider и не переносятся в
документацию или diagnostic report. После изменения проверьте status и
**Журналы**; при update отдельно убедитесь, что конфигурация сохранена.
