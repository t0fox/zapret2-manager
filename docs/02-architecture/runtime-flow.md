# Runtime flow: от LuCI до nfqws2

Эта страница показывает не список файлов, а **путь ответственности**: как действие пользователя проходит от LuCI до backend, где заканчивается безопасный preview, кто имеет право менять постоянное состояние и каким образом результат возвращается обратно в интерфейс.

Главная идея zapret2-manager: браузер не является владельцем runtime. Он формирует намерение, показывает состояние и вызывает ограниченные backend-операции. Каноническое состояние, транзакции, процессы и фактическое состояние nfqws2 проверяются на стороне backend/runtime.

```text
LuCI
  ↓
z2m-api.js / rpc.declare
  ↓
rpcd / ubus
  ↓
bounded CLI или модуль-владелец
  ↓
model / state / compiler / preflight
  ↓
Preview / Validate
  ↓
явная граница mutation
  ↓
snapshot + CAS / revision guard
  ↓
санкционированный writer или transient runtime owner
  ↓
zapret2 / nfqws2 / системный runtime
  ↓
observations + verification
  ↓
status projection
  ↓
LuCI
```

## 1. LuCI — потребитель, а не источник истины

Публичная UI-часть собрана вокруг LuCI JavaScript. Вызовы backend объявляются через `z2m-api.js` и стандартный для OpenWrt RPC-механизм. Страница может держать локальное состояние формы, выбранную вкладку или draft, но эти данные нельзя считать доказательством того, что конфигурация уже действует на роутере.

Это различие особенно важно при `Strategy` и `Scanner`. UI может показать кандидата, результат проверки или подготовленное изменение, но право на постоянную запись принадлежит не странице. После любой значимой mutation интерфейс должен перечитать состояние владельца, а не продолжать жить на основании оптимистичного локального объекта.

## 2. rpcd/ubus — ограниченная граница управления

LuCI обращается к rpcd/ubus facade. Его задача — принять ограниченную структуру запроса, проверить форму данных и передать работу конкретному модулю или CLI entry point. Это сознательно уже, чем «дать веб-интерфейсу shell».

Такая граница позволяет различать read-операции, preview/validation и mutation. Ошибка транспорта, validation или preflight не должна превращаться в частично применённую конфигурацию только потому, что кнопка уже была нажата.

Backend разбит по областям: Strategy/Profile, Scanner, jobs, DNS, domain/list management, proxy, maintenance и другие владельцы имеют отдельные функции и state. Это поддерживает принцип **single-writer**: для конкретной постоянной области должен быть один санкционированный путь записи, а соседний продукт не должен создавать параллельную скрытую mutation-модель.

## 3. До mutation: model, compile, preflight, Preview, Validate

Для Strategy сильная сторона текущего проекта — возможность пройти несколько стадий до постоянного изменения.

`compile` превращает продуктовую модель в исполнимое представление. `preflight` проверяет зависимости и допустимость кандидата. `Preview` нужен, чтобы увидеть вычисленный результат без применения. `Validate` отвечает на более строгий вопрос: допустим ли этот кандидат для дальнейшей mutation в текущем контексте.

Эти стадии нельзя путать с `Apply`. Успешный Preview означает только, что система смогла построить осмысленный кандидат. Успешный Validate не означает, что runtime уже изменён.

## 4. Apply — граница полномочий

Постоянная конфигурация Strategy проходит через существующий sanctioned apply path. Перед записью важны несколько защитных свойств: актуальность revision/hash, snapshot предыдущего состояния, preflight и контроль того, что операция относится именно к состоянию, которое пользователь видел перед Apply.

Именно здесь применяется CAS-подобная логика: если authoritative state успел измениться, старое намерение не должно молча перезаписать более новое состояние. Поэтому mutation — это не «записать JSON», а переход состояния с проверяемой исходной точкой.

После записи недостаточно получить `exit code 0`. Runtime должен быть перечитан и проверен: запуск процесса, ожидаемые runtime-признаки, согласованность применённой конфигурации и наблюдаемого состояния — отдельная стадия.

## 5. Verification и rollback

Транзакционный путь строится вокруг простой гарантии: **успех — это проверенный новый результат, ошибка — это проверяемое восстановление, а не неопределённое полусостояние**.

Поэтому snapshot нужен до mutation. Если после записи или restart verification не подтверждает ожидаемый результат, rollback должен восстанавливать именно сохранённое состояние, а затем система снова проверяет наблюдаемое состояние. Сам факт запуска rollback-команды ещё не доказывает восстановление.

Это одна из намеренных OpenWrt-native особенностей zapret2-manager: parity с внешним продуктом не требует копировать его внутренний control plane, если пользовательское поведение можно сохранить с более строгой transaction boundary.

## 6. Scanner использует другую mutation-модель

Scanner исследует кандидаты и поэтому не должен пользоваться постоянным Apply как циклом перебора. Для него существует **transient runtime lifecycle**. Кандидат получает временные ресурсы, выполняется в ограниченной A1 lifecycle, проверяется probes, после чего временные ресурсы обязаны пройти cleanup.

```text
candidate
  ↓
A1 transient ownership
  ↓
temporary runtime
  ↓
probes / evidence
  ↓
result
  ↓
cleanup
```

Полезный Scanner result может стать входом для Strategy handoff, но сам Scanner не получает право незаметно сделать найденный вариант постоянной конфигурацией. Для постоянного результата он должен вернуться в обычный Strategy lifecycle: Preview → Validate → Apply.

## 7. Почему A1 важен

A1 — это не просто имя процесса. Это долговечная единица владения transient runtime: protocol/schema, helper/runtime adapter и cleanup должны говорить об одной и той же lifecycle, иначе невозможно надёжно доказать, что временный процесс действительно принадлежит конкретной Scanner-попытке и был очищен именно её владельцем.

В текущем `main` уже присутствуют Scanner model, planner, generator, state, probes, worker, transient layer и runtime adapter, а последние Scanner-изменения усилили canonical A1 lifecycle и acceptance-tail проверки. Это существенный прогресс, но сам по себе он ещё не доказывает полный production E2E Scanner.

## 8. Ошибки и неопределённость

Backend должен различать ожидаемую продуктовую ошибку, конфликт revision, недоступную зависимость, failure runtime, failure cleanup и ситуацию, когда результат нельзя доказать. Последний случай особенно важен: **unknown не должен автоматически превращаться в success**.

Если приложение не может подтвердить ownership процесса или состояние временных ресурсов, безопаснее вернуть контролируемую ошибку/неопределённость и оставить дальнейшее решение владельцу lifecycle, чем продолжить destructive cleanup по широкому совпадению имени процесса.

## 9. Что считать доказанным

Разные уровни проверки отвечают на разные вопросы. Source test может доказать модель переходов. Integration test — контракт между компонентами. OpenWrt package build — совместимость с toolchain/package layout. Router E2E — фактическое поведение на target. Проверка живого трафика — уже свойства конкретной сети и runtime.

Поэтому архитектурная документация намеренно не делает вывод «компонент существует → функция production-ready». Для такого вывода нужен доказанный вертикальный путь от пользовательского действия до runtime и обратно.
